# Working on Bellatrix

This file is for coding agents (and people) changing this repository. Read
[README.md](README.md) for what the app is, then
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), which also lists where to change
common things.

## Two kinds of agent

The app itself runs coding agents on the phone, and they write widgets. That is
a different job from changing this code:

- **Writing or fixing a widget** (`*.owl`): the language is documented for
  agents in [app/src/main/assets/widgets/README.md](app/src/main/assets/widgets/README.md)
  and its `docs/` folder. Those files ship inside the app and are what agents on
  the phone read. A widget needs no Kotlin change.
- **Changing the launcher** (Kotlin, the OWL compiler, the Linux setup): this
  file.

The `AGENTS.md` that agents in the phone's Linux see is generated by
`app/src/main/kotlin/com/bellatrixos/widgets/WidgetEngine.kt`. It is not this
file.

## Build and test

**Do not run Gradle or other local build commands in this checkout.** All
builds, tests and linting run in GitHub Actions when changes are pushed. Local
work is source edits plus static checks (grep, file inspection); report compile
risks instead of trying to resolve them with a local build.

Releases are GitHub Releases tagged `v*`. There is no Play release track in this
repository; ignore any inherited Play/Foss flavour or workflow names.

- Tests live in `owl/src/test` (the language) and `app/src/test` (plain JVM
  tests). Add a test where the code allows one; CI runs them.
- `app/src/main/jniLibs/` (proot) and `local.properties` are gitignored. They are
  prepared in the build environment, not committed.
- On a device, `owl-check <file>` compiles a widget and renders a preview PNG;
  `owl-send <file> set <state> <value>` and `refresh` drive a running widget.

## Rules the code doesn't show

- **Bellatrix is the base; Omalauncher features are merged into it, never the
  other way round.** Keep Bellatrix's classic home (desktop icons, taskbar,
  start menu, app windows) as the visible launcher. A ported feature is added
  to those existing surfaces: guest apps and coding agents go in the same app
  drawer, settings in the same settings screens, windows in the same window
  layer. Never replace or hide the classic home, add a second home activity or
  Compose home over it, add a mode/enable switch, a parallel backend, a
  separate button or screen, or branching like `useOwlHome`/`LinuxRuntime`.
  One runtime, one Bellatrix home, one drawer, no user choice to make.
- **Merged features must use Bellatrix's UI, in every future release.** Never
  ship a ported screen that keeps Omalauncher's Compose/Material look, even if it
  is wrapped in a Bellatrix window or settings activity. Rebuild the feature
  with Bellatrix's own views (`UISettingsCard`, settings fragments,
  `UIFragment`/window cards, Bellatrix strings and style). Coding Agents is a
  standalone top-level Bellatrix Settings page built from those cards: never
  nested under Linux settings, never a separate Omalauncher-style screen.
- **Existing installs must keep working.** A change to saved data, the rootfs
  setup or files the launcher writes goes
  through one of the four update mechanisms in ARCHITECTURE.md "Updates": a new
  rootfs step id, a `Versioned` migration, or a `ManagedFiles` policy. Never
  delete an old reader.
- **OWL language level.** `Compiler.LEVEL` (owl module) is the language
  version. Anything a widget could depend on goes into the next unreleased
  level: if the current level has already shipped in a release (see
  CHANGELOG.md), bump it, otherwise add to it. Record the addition in `SINCE`
  (`owl/.../widgets/lang/Schema.kt`) and in
  `app/src/main/assets/widgets/docs/versions.md`.
- **The widget docs are part of the feature.** A language change updates the
  matching page in `app/src/main/assets/widgets/docs/`. Agents on the phone
  only know what's written there.
- **No `inline` functions in owl that the app calls.** owl builds for JVM 17,
  the app for JVM 11, so an inline owl function fails the app build
  (`INLINE_FROM_HIGHER_PLATFORM`). Write a plain method instead.
- **UI text goes in `res/values/strings_<area>.xml`**, with a translation in
  every `values-*` folder (de, es, in, pt, zh). `HardcodedTextTest` fails on
  literal text in UI calls. German is lower case wherever the English is, and
  casual (du). Agent prompts, owl errors, logs and the stock `.owl` files stay
  English.
- **Don't enable `generateLocaleConfig`.** With a locale config, changing the
  app language in Android Settings crashes Settings for a launcher.
- **Fix what's asked.** Don't change behavior or add mechanisms beyond the
  task. Mention anything else you notice instead of changing it.

## Commits and releases

Write a short subject line about the user-visible change and why. Stage files
by name, not with `git add -A`. CI verifies pushes; publish by tagging `v*` and
creating the matching GitHub Release.
